# Report page structure (one notebook or script)

Defaults for a report page. Research is fluid: use the parts that help the reader follow the
argument, reshape or drop the others. The principles are firmer than the outline.

## Principles

1. **Question first.** Most steps answer a question. The heading of a step is usually that
   question. Validation and descriptive EDA steps can have a descriptive heading.
2. **Context just in time.** Methods, math and data subsets go in the step that needs them. Up
   front: only the data overview and the shared model or definitions. A reader who opens one
   step must not need the other steps, also when this repeats details.
3. **Order by the argument.** Usually setup and validation, then the main results, then the
   explanations of those results. The notebook order can be a good order; do not assume it.
4. **Show everything, clearly.** Every figure and table of the notebook or script is on the
   page (tangential or redundant ones in the appendix), except what Aviv says to skip and WIP
   results. Numbers go in tables, not only in prose.
5. **Facts apart from interpretation.** Observations are facts with numbers. Conclusions are
   interpretation, and only the ones Aviv agreed to. Mark a hypothesis as a hypothesis.
6. **Unexpected findings get documented.** They feed future work.
7. **Methods are complete and exact.** A reader can do the analysis again from the page alone,
   and can find where a result could be wrong.

## Outline

1. **Provenance** (gray, first line): "Generated by Claude from `<notebook or script>` at
   `<repo>@<sha>`, ... (each repo the analysis uses; "+ local changes" if the working tree has
   changes). Runs: `<ids>`. Last update `<date>`." A link back to `index.html`.
2. **Questions:** the question(s) of the analysis that this notebook addresses, one line each,
   as in the index.
3. **Table of contents** (links to the step anchors).
4. **Data overview:** the runs, cohorts and splits, with a table of counts (subjects, sessions)
   per cohort and split. Short: the exact data and filters of each step are in its Methods.
5. **Shared model or definitions** (only if several steps use them): for example a signal model
   that predicts what each figure should show. A model that makes predictions is the strongest
   frame: later steps confirm or break it.
6. **Steps,** ordered by the argument (see "Step block"). Group related steps under one heading
   with a sub-question when it helps.
7. **Other findings:** unexpected observations, with links to their steps.
8. **Open questions and next checks,** ordered by value. WIP results are listed here as pending.
9. **Appendix** (collapsed): metric definitions, per-session or per-condition figures, items
   left out of the main flow, reproducibility (notebook, commits, run ids, data snapshot date,
   changelog).

Question-level parts (motivation, short answer, global conclusions, caveats) are in the index
(`index.md`).

## Step block

Core parts:

- **Heading:** a number and the question or check, e.g. `2. Does the gap shrink with
  lambda?` (no "Step" word), with a stable anchor (`id="s2"`) so the index and the hub can link
  to it. Sub-steps: `2.1`, `2.2`.
- **Why:** 1-2 lines. What this result probes, and how it helps answer the question.
- **How:** 1-2 sentences in simple words, with the one equation the reader needs. Directly
  after it, the **Methods** toggle with the full methods of the step (see "Methods"). Aviv opens
  it when he asks how a result was made.
- **Figure(s) or table(s).** Caption: one line on what it shows. Directly below:
  **How to interpret** (axes, colors, what one point or curve is, what "good" or "no effect"
  looks like). For a table: what each column means, and the rule for bold values.
- **Observations:** facts only. The few most important ones, with numbers only where they add
  to the figure or table.

Add when they apply:

- **Expectation** (before the figure): what we expect if the hypothesis is true, from the
  spec's predictions, so the reader can see a surprise. Usually not needed for a sanity check.
- **Conclusion** (local): only as agreed with Aviv; else "Conclusion: not yet discussed".

Two related figures can share one "Why" and one "How".

## Methods

The Methods toggle of each step holds all the details needed to do the analysis again. Write it
from the code, not from the notebook markdown. If the code does not show a detail, write
"unknown" and ask Aviv. Never guess.

**Checklist** (each item, or "n/a"; the repo conventions in `CLAUDE.local.md` can add items):
- **Data:**
  - the runs: their ids, and the checkpoint or epoch;
  - the split (train / val / test);
  - the cohorts or data subsets, their inclusion criteria, and their filters;
  - the unit of analysis (e.g. epoch, segment, session, subject), and the counts at that unit;
  - the representation (e.g. an embedding view), and its dimension.
- **Processing:** each filter, rejection rule, normalization, aggregation and matching step,
  in order. For each rejection, the counts before and after.
- **Math:**
  - block equations for the key quantities, inline math for small ones;
  - each symbol defined where it first appears: what it is, its shape, and its index sets
    (e.g. "$X \in \mathbb{R}^{n \times d}$: the sample embeddings of the test set, one row per
    sample");
  - the estimator, not only the quantity (e.g. the unbiased MMD estimator, the kernel, the
    bandwidth rule);
  - the statistics: the test, the CI method, the number of resamples or folds, the seeds.
- **Math to code and data:**
  - for each equation, the function that implements it (`module.py:function`);
  - the implementation choices that can change the result, e.g. what data a transform is fitted
    on (in-sample or out-of-sample), how pairs or samples are drawn, how the data is weighted;
  - where the code differs from the usual textbook form, and why;
  - each parameter value, with the reason for it.
- No copied code blocks. Describe the approach where it matters for the result.

A long Methods toggle is fine: use the toggle for length, not for less detail.

## HTML layout

- One HTML file per page, a complete document (`<!doctype html>`, `<title>`, inline
  `<style>`). Plain HTML and CSS, readable width, a sticky or top table of contents for long
  pages. Utilitarian treatment: polished type and spacing, no hero, no decoration.
- **Publish-ready by default.** Follow the Artifact page contract where it costs nothing, so a
  page can be published later with no rewrite: colors as tokens on `:root` with the two dark-mode
  blocks and an explicit `body` background, a 16px side gutter, wide tables in their own
  `overflow-x: auto` container, a `<title>` that is a short name (e.g. "Headset metrics 020"),
  scripts only from cdnjs (or jsDelivr, unpkg), pinned to an exact version. The
  `artifact-design` skill has the full contract and the design guidance: load it when you set up
  the page style of an analysis, or when a design or layout question comes up.
- **Toggles** (`<details>`): Methods, long derivations, metric definitions, per-session
  figures, the appendix.
- **Tabs:** variants of the same figure (per session, per array, train/test, per baseline).
- **Side by side:** two figures that the reader must compare.
- **Callouts:** blue = questions or short answer, yellow = caveat, green = recommendation.
- **Figures:** `<figure>` with a relative `<img src>` to the saved file and a `<figcaption>`.
- **Tables:** all key numbers. Add a noise floor or null column when one exists.
- **Math:** MathJax 3 with SVG output (`tex-svg.js` from cdnjs, pinned), with `$...$` and
  `$$...$$` (enable `$` as an inline delimiter in its config). Not KaTeX: KaTeX needs a
  stylesheet and fonts from a CDN, which a published Artifact blocks.
- **Interactive plots** (Plotly, D3) only where interaction helps: sliders, hover, filters.
  Their data goes inline or in a `<script src="data.js">` file (a page opened from disk cannot
  `fetch()` local files). For their form, colors and hover, use the `dataviz` skill. For titles,
  axis units, named statistics and legends, use `self-explanatory-figures`; it wins where the
  two disagree.
- **Diagrams** (a method, a pipeline, a data split): inline SVG, with the `artifact-diagramming`
  skill. Static PNG figures from the analysis code follow `self-explanatory-figures`.

## Writing rules

- ASD-STE100: short sentences, simple words, active voice, bullets over prose.
- No em or en dashes. Keyboard characters only.
- Verb strength matches the evidence: "reduces", not "removes"; "is consistent with", not
  "shows", when other explanations are open; "no change beyond noise", not "no effect".
- Numbers: give units, and the noise floor or null next to a difference. Say "within noise"
  when it is.
- Use the code names of metrics and variables in `backticks`, and define each one where it
  first appears.

## Common mistakes

| Mistake | Fix |
|---|---|
| "Bandpass filter", "we use MMD", "z-scored" with no details | Give the filter parameters, the estimator and kernel, what the mean and SD are computed over |
| Counts that change between steps with no reason | List each filter with the counts before and after |
| The same result described in several places (curve list, table, summary) | One step per result. Others cite it, they do not restate it |
| "Panel 1: X. Panel 2: Y." as the description of a figure | "How to interpret" once, then observations about what the figure shows |
