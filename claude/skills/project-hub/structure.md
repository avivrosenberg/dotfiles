# Page structure (Notion)

The page design comes from the `research-collab-report` skill. Read its `report.md` (principles,
step block, Methods checklist, writing rules, common mistakes) and `index.md` (question-level
parts) first. This file adds only what is specific to Notion: the hub, how a sub-page maps to
the reports, flag markers and the Notion layout. Research is fluid: reshape or drop parts that
do not help the reader.

## Hub page (project)

The hub tracks the project: where it is, what we know, and the evidence. It has no methods:
the methods are in the sub-pages. Each claim on the hub links the sub-page section that
supports it.

1. **Provenance line** (gray text, first line): "Maintained by Claude from the sub-pages
   below. Sources: `<repo>:<analysis folder>`, ... Last update `<date>`." Each source is a repo
   name and a path relative to the repo root, never a local path.
2. **Context:** 2-4 lines. Why this project matters, what the problem is.
3. **Goals:** clear, testable goals. Aviv approves each goal.
4. **Status:** 2-4 lines. The progress against each goal, the main open problem, and the next
   experiments.
5. **Questions table:** one row per project question. Aviv approves each question.

   | # | Question | Current best answer | Status | Evidence |
   |---|---|---|---|---|
   | Q1 | Does augmentation X reduce the train/test gap? | Yes, in location, not in spread (conditional on F3) | partly answered | [Domain gap, 2](...), [Eval metrics, 4](...) |

   - **Current best answer:** 1-2 short sentences, with the main number if it helps.
   - **Status:** `open` (no evidence yet), `partly answered`, `answered`, or `contradicted`
     (sub-pages disagree).
   - **Evidence:** links to sub-page sections, not only to pages.
6. **Question details:** one H2 per question, `Q1. <question>`, in the table order:
   - **Answer:** the current best answer, a little longer than in the table if needed.
   - **Evidence for:** bullets. Each bullet gives the result, its key number, and a link to
     its section.
   - **Evidence against or open:** results that weaken the answer, other explanations, and
     contradictions between pages.
   - **Open flags:** the review flags that affect the answer, with links.
   - **Next check:** what would change the answer, and the experiment that can test it.
7. **Leads:** unexpected findings and open questions from the sub-pages. One line each, with a
   link to the source step.
8. **Sub-pages:** the list of experiment pages, newest last, each with its question.
9. **Review:** a link to the Review page (if it exists).

## Sub-page (experiment)

A sub-page answers one experiment question. It combines the question-level parts of the index
(`index.md`) with the steps of the reports that address that question (`report.md`), in the
order of the argument. If the reports exist, take the text from them; else write the same parts
from the code and outputs.

1. **Provenance line** (gray text, first line): "Generated by Claude from `<notebook(s)>` at
   `<repo>@<sha>`, ... ("+ local changes" if the working tree has changes). Last update
   `<date>`."
2. **Short-answer callout** (blue), from the index.
3. **Table of contents.**
4. **Motivation,** from the index.
5. **Data overview** and **shared model or definitions,** from the reports (merge them if
   several reports feed the page).
6. **Steps,** in the step-block format of `report.md`, renumbered for this page. Each section
   that has open review flags ends with a flag marker.
7. **Conclusions** (global), **other findings**, **caveats** (strongest case against in a yellow
   callout), **open questions and next checks**: from the index, only the items of this
   question.
8. **Appendix** (toggles): as in the reports, with one reproducibility toggle for the page.

The Methods toggle stays directly after the "How" sentence of each step. Never move it to a
separate page: Aviv opens it live when asked how a result was made.

## Flag markers

Review flags live on the project Review page, which the `project-hub-review` skill writes.
In an experiment page, each section that has open flags ends with one gray marker line that
links to the flag details:

```
<p color="gray">
⚑ [F3](<review page url>#<block id>) null weights, [F5](<...>) offset bias
</p>
```

- A flag with a fix that waits for review shows as pending: `⚑ [F3](...) null weights (fix
  pending review)`.
- The review skill adds and removes markers. The `project-hub` skill keeps them, moves them with their
  section, and marks a flag as pending when an update fixes it.
- A conclusion that depends on a flagged result says so ("conditional on F3").

## Notion layout tools

The Notion form of the HTML layout in `report.md`:
- **Tabs:** variants of the same figure (per session, per array, train/test, per baseline).
- **Columns:** two figures that the reader must compare side by side.
- **Toggles and toggle headings:** Methods, long derivations, metric definitions,
  per-session figures. A toggle heading can hold a whole secondary step.
- **Callouts:** blue = short answer, yellow = caveat / strongest case against,
  green = recommendation for the team.
- **Math:** see `notion.md` for the syntax.
