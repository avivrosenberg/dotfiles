# Page structure

Defaults for the hub, the sub-page and the step. Research is fluid: use the parts that help the
reader follow the argument, reshape or drop the others. The principles below are firmer than
the outlines.

## Principles

1. **Question first.** Each page and most steps answer a question. The heading of a step
   is usually that question. Validation steps and descriptive EDA steps can have a
   descriptive heading.
2. **Local vs global.** A step gives a local conclusion. The experiment gives global
   conclusions that combine local ones to answer the main question. Global conclusions are
   always in service of the question.
3. **Context just in time.** Put methods, math and data subsets in the step that needs them.
   Up front: only an overview of the data and the shared model or definitions that several
   steps use. The full methods of each step are in that step, also when this repeats details
   of another step: a reader who opens one step must not need the other steps.
4. **Order step by step.** Each step builds on the previous steps: usually setup and
   validation, then the main results, then the explanations of those results. The notebook
   order can be a good order, but do not assume it.
5. **Show everything, clearly.** Every figure and table goes on the page (tangential or
   redundant ones in the appendix). Numbers go in tables, not only in prose. The reader must
   not miss a result.
6. **Facts apart from interpretation.** Observations are facts with numbers. Conclusions are
   interpretation. Mark a hypothesis as a hypothesis.
7. **Unexpected findings get documented.** They do not answer the question, but they feed
   future work.
8. **Methods are complete and exact.** A reader can do the analysis again from the page alone,
   and can find where a result could be wrong. See "Methods" below.

## Hub page (project)

The hub tracks the project: where it is, what we know, and the evidence. It has no methods:
the methods are in the sub-pages. Each claim on the hub links the sub-page section that
supports it.

1. **Provenance line** (gray text, first line): "Maintained by Claude from the sub-pages
   below. Sources: `<repo>:<analysis folder>`, ... Last update `<date>`." Each source is a repo
   name and a path relative to the repo root, never a local path.
2. **Context:** 2-4 lines. Why this project matters, what the problem is.
3. **Goals:** clear, testable goals (for example "better `ssl_il` metrics, with no PH cost and no
   PTSD degradation"). Aviv approves each goal.
4. **Status:** 2-4 lines. The progress against each goal, the main open problem, and the next
   experiments.
5. **Questions table:** one row per project question. Aviv approves each question.

   | # | Question | Current best answer | Status | Evidence |
   |---|---|---|---|---|
   | Q1 | Does more IL in training move IL away from PH? | Yes, in location, not in spread (conditional on F3) | partly answered | [Embedding gap, 2](...), [IL metrics, 4](...) |

   - **Current best answer:** 1-2 short sentences, with the main number if it helps.
   - **Status:** `open` (no evidence yet), `partly answered`, `answered`, or `contradicted`
     (sub-pages disagree).
   - **Evidence:** links to sub-page sections, not only to pages.
6. **Question details:** one H2 per question, `Q1. <question>`, in the table order:
   - **Answer:** the current best answer, a little longer than in the table if needed.
   - **Evidence for:** bullets. Each bullet gives the result, its key number, and a link to
     its section.
   - **Evidence against or open:** results that weaken the answer, other explanations, and
     contradictions between pages.
   - **Open flags:** the review flags that affect the answer, with links.
   - **Next check:** what would change the answer, and the experiment that can test it.
7. **Leads:** unexpected findings and open questions from the sub-pages. One line each, with a
   link to the source step.
8. **Sub-pages:** the list of experiment pages, newest last, each with its question.
9. **Review:** a link to the Review page (if it exists).

## Sub-page (experiment)

Default outline:

1. **Provenance line** (gray text, first line): "Generated by Claude from `<notebook(s)>` at
   `<repo>@<sha>`, ... (one for each repo that the analysis uses; add "+ local changes" if the
   working tree has changes). Last update `<date>`."
2. **Short-answer callout** (blue): the question(s) and a short answer for each, 1-3 lines. Add
   a line for an important unexpected finding.
3. **Table of contents.**
4. **Motivation:** why this question matters for the project, and the specific sub-questions.
5. **Data overview:** the runs, cohorts and splits that the page uses, with a table of counts
   (subjects, sessions) per cohort and split. A short overview only: the exact data and filters
   of each step are in its Methods toggle.
6. **Shared model or definitions** (only if several steps use them): for example a signal model
   that predicts what each figure should show, or the definition of the views that all steps
   compare. A model that makes predictions is the strongest frame: later steps then confirm or
   break it.
7. **Steps,** ordered by the argument. Group related steps under one H2 with a sub-question when
   it helps. A group gets a short combined conclusion.
8. **Conclusions** (global): numbered. Each one answers (part of) the main question and links the
   steps that support it.
9. **Other findings:** unexpected observations that do not answer the question, with links to
   their steps.
10. **Caveats and limitations,** with the strongest case against the main conclusion in a yellow
    callout.
11. **Open questions and next checks:** what to do next, ordered by value.
12. **Appendix** (toggles): metric definitions, per-session or per-condition figures, items left
    out of the main flow, and the reproducibility toggle (notebooks, commit, run ids, data
    snapshot date, changelog).

## Step block

Use this shape as a guideline for each step. Drop or reshape parts that do not apply (for
example, a sanity check usually needs no expectation, and a step with two related figures can
share one "Why" and one "How").

- **Heading:** a number and the question or check, for example `# 1. Can we trust the
  embeddings?` (no "Step" word). Grouped sections use H2 with the same numbering. The numbers
  let the conclusions refer to sections ("section 2").
- **Why:** 1-2 lines. What this result probes, and how it helps answer the main question.
- **Expectation:** what we expect to see if the model or hypothesis is true. Write it before the
  figure, so the reader can see if the result is a surprise.
- **How:** 1-2 sentences in the main flow. The method in simple words, with the one equation
  that the reader needs to understand the result.
- **Methods** toggle, directly after the "How" sentence: the full methods of this step (see
  "Methods" below).
- **Figure(s) or table(s).** Directly below each figure: **How to interpret** (axes, colors,
  what one point or curve is, what "good" looks like). For a table: what each column means, and
  the rule for bold values.
- **Observations:** facts only, short and focused. Highlight the few most important facts; do
  not describe everything in the figure or table. Give a number only when it adds clarity
  beyond what the figure or table already shows.
- **Conclusion** (local): what this result means for the step question. Mark hypotheses.
- **Flag marker** (if the section has open flags), as the last line (see "Flag markers").

## Methods

The sub-pages are Aviv's reference for the methods, and the base on which he scrutinizes the
results. The Methods toggle of each step must hold all the details needed to do the analysis
again. Write it from the code, not from the notebook markdown. If the code does not show a
detail, write "unknown" and ask Aviv. Never guess.

**Checklist** (each item, or "n/a"; the repo conventions in `.claude/project-hub.md` can add
items):
- **Data:**
  - the runs: their ids, and the checkpoint or epoch;
  - the split (train / val / test);
  - the cohorts or data subsets, their inclusion criteria, and their filters;
  - the unit of analysis (for example epoch, segment, session, subject), and the counts at
    that unit;
  - the representation (for example an embedding view), and its dimension.
- **Processing:** each filter, data rejection rule, normalization, aggregation and matching
  step, in order. For each rejection, the counts before and after.
- **Math:**
  - block equations for the key quantities, inline math for small ones;
  - each symbol defined where it first appears: what it is, its shape, and its index sets (for
    example "$X \in \mathbb{R}^{n \times d}$: the session embeddings of the PH test set, one
    row per session");
  - the estimator, not only the quantity (for example the unbiased MMD estimator, the kernel,
    and the bandwidth rule);
  - the statistics: the test, the CI method, the number of resamples or folds, the seeds.
- **Math to code and data:**
  - for each equation, the function that implements it (`module.py:function`);
  - the implementation choices that can change the result, for example what data a transform
    is fitted on (in-sample or out-of-sample), how pairs or samples are drawn, or how the
    data is weighted;
  - where the code differs from the usual textbook form, and why;
  - each parameter value, with the reason for it.
- No copied code blocks. Describe the approach where it matters for the result.

Use the toggle for length, not for less detail: a long Methods toggle is fine.

## Flag markers

Review flags live on the project Review page, which the `project-hub-review` skill writes.
In an experiment page, each section that has open flags ends with one gray marker line that
links to the flag details:

```
<p color="gray">
⚑ [F3](<review page url>#<block id>) null weights, [F5](<...>) offset bias
</p>
```

- A flag with a fix that waits for review shows as pending: `⚑ [F3](...) null weights (fix
  pending review)`.
- The review skill adds and removes markers. The report skill keeps them, moves them with their
  section, and marks a flag as pending when an update fixes it.
- A conclusion that depends on a flagged result says so ("conditional on F3").

## Notion layout tools

Use them to make the page less dense and the main flow short:
- **Tabs:** variants of the same figure (per session, per array, train/test, per baseline).
- **Columns:** two figures that the reader must compare side by side.
- **Toggles and toggle headings:** long derivations, metric definitions, per-session figures,
  raw traces. A toggle heading can hold a whole secondary step.
- **Callouts:** blue = short answer, yellow = caveat / strongest case against,
  green = recommendation for the team (for example "Recommendation for DCX").
- **Tables:** all key numbers. Add a noise floor or null column when one exists.

## Writing rules

- ASD-STE100: short sentences, simple words, active voice, bullets over prose.
- No em or en dashes. Use keyboard characters only.
- Numbers: give units, and the noise floor or null next to a difference. Say "within noise"
  when it is.
- Use the code names of metrics and variables in `backticks`, and define each one where it
  first appears.
- Figure captions: one line on what the figure shows. The "How to interpret" text goes below.

## Common mistakes

| Mistake | Fix |
|---|---|
| All methods and data up front, far from the results | Put each method in the Methods toggle of the step that uses it |
| "Bandpass filter", "we use MMD", "z-scored" with no details | Give the filter parameters, the estimator and kernel, what the mean and SD are computed over |
| A symbol with no definition, or no shape | Define each symbol where it first appears, with its shape and index sets |
| Counts that change between steps with no reason | List each filter with the counts before and after |
| Methods copied from the notebook markdown | Write them from the code, and name the function for each equation |
| A method detail that is guessed | Write "unknown" and ask Aviv |
| A hub answer with no link, or stronger than its sub-pages | Link the sections; match the strength of the sub-page conclusions |
| Methods on the hub | Methods only in the sub-pages; the hub links them |
| Steps in notebook order without a check | Order step by step, each step building on the previous ones |
| The same result described in several places (curve list, table, summary) | One step per result. The global conclusions cite it, they do not restate it |
| "Panel 1: X. Panel 2: Y." as the description of a figure | "How to interpret" once, then observations about what the figure shows |
| Observations that restate every value in the figure or table | The few most important facts, with numbers only where they add clarity |
| Observations and conclusions in one paragraph | Separate **Observations** and **Conclusion** |
| No expectation, so a surprise looks like a normal result | Write the expectation before the figure |
| A figure or table from the notebook is missing | Put it in the main flow or the appendix, or list it as left out, with the reason |
| Long text-only pages | Tabs, columns and toggles for variants and details |
| Conclusions far from their evidence | Local conclusion in the step. Global conclusions link the sections |
| A conclusion stronger than its section's flag allows | Make it conditional or a hypothesis |
| "Step N:" in headings | "N. Question?" |
